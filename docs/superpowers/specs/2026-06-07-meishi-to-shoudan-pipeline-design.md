## 0. 背景と「真実の置き場」

このプロダクトの売りは「**名刺から営業トークまでの一連の流れ**」と「**AIが情報を拾ってスコアリングする評価**」。
しかし現状、器（Notionプロパティ・型・足場）は大量に作られているが、**中身の配線が通っていない**箇所が複数あることがコード調査で確定した。

**原則（以後ぶれさせない）**: 仕様・進捗の真実は「人やAIの記憶・報告」ではなく「**コードと実機の動作**」に置く。
本設計に基づく実装は、口頭の完了報告を禁止し、**テスト＋実際に動かしたNotion結果**を証拠として提示する（superpowers: verification-before-completion / TDD に準拠）。

### 現状のコード事実（裏取り済み）
- 企業リサーチの外部AIは **Perplexityではなく Gemini**（`researchCompanyWithGemini` src/index.ts:14472, `gemini-2.5-flash` :14476）。**web検索グラウンディングなし**＝会社名/ドメイン/住所の3点からの推測生成。
- **TDB（帝国データバンク）連携は未実装**。`TDB企業コード`等のプロパティは存在するが、取得・書き込みコードは皆無。
- `Research` 型は**テキスト9項目のみ**（src/index.ts:354-364）。役員・SNS・財務・与信・ニュースは型に存在しない。
- 名刺処理は `enrichCompany`（src/index.ts:14325-14352）でリサーチを1回呼び、**無条件で `企業調査ステータス＝完了`** にする（:14335）。
- 商談準備レポート `processMeetingPrepReport`（src/index.ts:6455）は **企業マスター＋外部Gemini**（`enrichCompanyForMeetingPrep` :9046→`researchCompany`）しか見ず、**商談履歴・成約/失注を一切参照しない**。
- `ナレッジ貢献スコア` は**読むだけ**で加算処理が存在しない（参照: src/index.ts:5821, 6204）。
- `AI学習ログDB` は**書き込み専用**で読み返し（検索・活用）処理が存在しない（生成: :3786,:3872,:3899／重複チェック: :3926,:3950,:12222）。

### 確定済みの方針判断（本セッション）
- 外部AIは **Perplexity 廉価版 `sonar`**（OpenAI互換API・**citations＝出典URLをネイティブ返却**）に切替。1回約0.25円。
- 役員・SNSは **公開情報かつ事業・経営に関する範囲のみ**取得（私生活・非公開は除外、社内利用限定）。
- TDBは **API契約済み・キーあり**（前提）。
- 出力は **ハイブリッド**（構造化列 ＋ ページ本文ドシエ ＋ 出典URL）。
- リサーチは **多段（観点別を並列実行）**。精度最優先、処理時間は許容（ステータス「調査中」表示）。

## 2. 🟦 ライン1：名刺 → 企業（外部リサーチ＋与信スコアリング）

### フロー（目標）
1. **起動**: 名刺登録Webhook。重複ガードで企業マスター照合／新規作成。`企業調査ステータス＝解析開始`。
2. **簡易エンリッチ**: Perplexity軽量1発で 概要・業種・所在・各URL（ウェブ/ X / LinkedIn）を即時に埋める（スピード重視）。
3. **TDB与信**: TDB API → 約8項目を構造化列へ。
   - 取得想定: **企業評点・倒産確率（評価点系）・年商（売上規模）・資本金・従業員規模・設立年月・業種・代表者／法人番号**。
   - 書き込み列: `資本金` `設立年月` `売上規模` `従業員規模` `業種` `代表者` `法人番号（TDB）` `TDB企業コード` `TDB収録業績期` `TDB調査年月日`。
   - （※実際の8項目は契約プランの返却仕様に合わせて確定。差異はTDB標準項目で補完。）
4. **スコアリング（売りの核）**: TDB評点＋倒産確率から
   - `信頼度`（高/中/低）を自動判定。
   - `提案可否`（提案可能／タイミング待ち／提案不可）を自動判定。
   - 判定根拠を `売買区分根拠`／`企業AI受付メモ` 等に明記。
5. **深掘り（多段Perplexity・並列実行）**: 観点別クエリを同時発射し、合計時間を最遅1本に圧縮。
   - 役員・キーパーソンのプロフィール
   - 役員・会社の公開SNS発信（X / LinkedIn / note / FB / YouTube）※事業・経営に関する範囲
   - 直近ニュース・プレスリリース（日付つき）
   - 再エネ／蓄電池との接点（屋根・遊休地・電力使用・脱炭素方針・補助金交付歴）
   - 想定決裁者の推定
   - **全項目に出典URL（Perplexity citations）を必須化**。裏取り不能は「推測ですが」と明記し断定しない。
6. **統合→出力（ハイブリッド）**:
   - 既存9テキスト列（`企業サマリー` `現在/将来課題仮説` `営業切り口` `和上解決策適合` `3C×3` `根拠ソース`）を更新。
   - 新規列（最小限）: `経営陣` / `役員SNS発信メモ` / `直近ニュース` / `再エネ接点シグナル` / `想定決裁者` / `想定反論・懸念` / `リサーチ最終実行日`(date)。
   - 既存URL列 `X（Twitter）` `LinkedIn` `ウェブサイトURL` を埋める。
   - ページ本文に「**企業ドシエ＋トーク土台**」を出典リンク付きで生成。
   - **マージ規則**: 既存に手入力値があれば上書きしない（`mergeCompanyResearch` の非破壊方針を踏襲）。
7. **完了判定**: 必須項目が揃い信頼度が確保できれば `完了`、不足・低信頼は `要確認` で停止（**無条件完了をやめる**）。

### 和上ナレッジ注入（精度の肝）
- リサーチ統合・トーク生成のプロンプトに **和上の営業プレイブック**（800MW実績／系統用蓄電池／発電所仲介・売買／FIP／高圧・低圧／投資回収シミュ／想定反論集）を埋め込み、「この会社のこの課題に、和上のこれが、この数字で効く」を必ずマッピングさせる。

## 3. 🟩 ライン2：→ 商談前（社内ナレッジでトーク最適化）

### フロー（目標）
1. **起動**: 商談準備レポートのボタンWebhook。対象企業を特定。`ステータス＝準備中（調査中）`。
2. **社内データのみ収集（外部は取得しない）**:
   - 企業DB（ライン1の成果＝ドシエ含む）
   - 商談履歴（`関連商談` ＋ `関連会議`議事録）
   - **成約履歴・失注履歴**（成約報告DB／案件管理DBの失注）
   - **AI学習ログDB**（読み返して活用＝死蔵解消）
   - 営業トーク管理DB（実戦トーク）
   - ※ `enrichCompanyForMeetingPrep` の**外部Gemini呼び出しは撤去**。
3. **勝ち筋／負け筋マッチング**: 似た業種・規模・売買区分の過去成約/失注から「効いた切り口」「地雷」を抽出。
4. **AI生成（OpenAI または Perplexity）**: 3C分析・商談仮説・ヒアリングリスト・注意点/リスク・**決裁者別トークスクリプト**。すべて社内事実ベース。
   - 書き込み列: 商談準備レポートDB の `3C分析` `商談仮説` `ヒアリングリスト` `注意点・リスク` `企業プロフィール`、本文へドシエ追記。
5. **自己採点ループ**: 生成物を別パスで「一般論か／根拠はあるか／粒度は商談レベルか」採点→不足なら書き直し（既存の二次レビュー発想を転用）。
6. **完了**: `準備完了`／不足は `要確認`。

## 5. 外部連携の実装方針

- **Perplexity**: `https://api.perplexity.ai/chat/completions`（OpenAI互換）、モデル `sonar`。`citations` を出典として各項目へ保存。`PERPLEXITY_API_KEY` はWorker環境変数。
- **TDB**: 契約API経由。`TDB_API_KEY`（仮）等をWorker環境変数。返却項目を内部の `TdbProfile` 型へ正規化。
- **非同期/タイムアウト**: 多段クエリは並列実行（`Promise.all`）で合計時間を最遅1本へ圧縮し、原則1回のWebhook処理で完結。超過時は「観点1つ＝1呼び出し」のチャンク方式（ステータスで進捗管理）へフォールバック。

## 6. エラー処理・安全
- 各外部呼び出しは失敗時に**安全フォールバック**（Perplexity失敗→既存ロジック、TDB失敗→Perplexity推定）で**止まらない**。失敗は `要確認` とメモで明示。
- 出典の無い断定をしない（会社ルール「根拠のない断定をしない」準拠）。役員情報は公開・事業範囲限定。
- 顧客・契約の個人情報を外部へ送らない（検索クエリは会社名・公開役員名・ドメイン・住所に限定）。

## 7. テスト方針
- 各ラインに対し: (a) 入力読み取り (b) 外部API呼び出し（モック） (c) スコアリング判定 (d) 出力書き込み (e) マージ非破壊 (f) フォールバック、をユニットテストで担保（既存 `src/*.test.ts` の様式に合わせる）。
- 完了の定義 = テスト緑 ＋ **実機で名刺1件→企業ドシエ生成、企業1件→商談準備レポート生成を実行し、Notion結果を提示**。
